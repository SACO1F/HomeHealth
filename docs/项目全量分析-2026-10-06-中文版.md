## 一、项目是什么

HomeHealth（家庭健康管家）是一款**本地优先、隐私至上的 Android 家庭健康管理应用**。拍摄体检报告照片 → 视觉大模型以 JSON 模式提取结构化指标 → 归一化层统一指标名与单位 → 用户核对确认 → 数据落入设备本地 Room 数据库。在此之上还有：趋势图、三规则异常检测、中英双语界面、用药提醒，以及一个在「关键词检索」与「手写 ReAct Agent」之间路由的健康问答功能。

这是一个**个人独立完成的、作品集/面试级项目**——`docs/` 目录同时包含面试准备材料（Agent 岗面试指南、100 题题库、考纲映射），这也解释了许多刻意的工程决策。

## 四、核心流程

### 4.1 报告解析（刻意非流式）
`拍照 → saveImageAndCreateDocument（UUID 文件名）→ 压缩为 base64 → 视觉模型（JSON 模式，temperature 0.1，maxTokens 4096）→ parseRecordsJson（括号配平提取 JSON，容忍 ```json 包裹）→ 逐条 SchemaNormalizer.normalize → 可编辑卡片 → confirmRecords`。
- `confirmRecords` 用 `database.withTransaction { deleteBySourceDocument + insertAll + update(COMPLETED) }` 包裹——堵住了此前已识别的「重复入库」漏洞。
- `rawText` 与 `normalizationNotesJson` 现已落库（DB v9），支持审计与回放。
- 卡在 `PROCESSING` 的僵尸文档会被重置为 `FAILED`，且带**限频 + 跳过在飞解析**两道保护。
- `DocumentUploadViewModel.parseInternal` 捕获 `Throwable`（含 `OutOfMemoryError`）→ 转为可重试失败态。

### 4.2 健康问答（流式，两条路径 + 兜底）
`QARepositoryImpl.askStream` 的路由：
1. **快路径**——问题含**强指标词**（`QaRetriever.strongTermsOf`）→ 对成员记录做 BM25 Top-12 检索 → SSE 流式，强制 `[n]` 引用。
2. **Agent 路径**——无强指标词但有数据/图片 → 手写 ReAct 循环（`ReActAgent`，≤5 轮、≤8 次工具调用），4 个只读工具（`search_records` / `get_reference_range` / `get_alerts` / `read_report_image`）。
3. **离线兜底**——未配 Key / 无记录 / 失败 → `LocalQaEngine` 规则引擎。

关键设计：**「数据依据」块在首个 token 之前先给出**（来自本地检索、总是可用）；检索路径的 `[n]` 与记录一一对应；Agent 的最终回答整段提交而非逐字上屏（只有轮次结束才知道它是否为最终回答）；最后一轮撤掉工具声明，让「轮数用尽」与「正常收尾」走同一条路径。

### 4.3 异常检测（三条规则）
`DetectAnomaliesUseCase`：**(1) 越界**（按性别取参考范围；比较符保守处理——`<0.1` 只有在边界值本身已越界时才报警）；**(2) 趋势**（连续 3 次同向、累计变化 ≥ 指标阈值、且落在 180 天窗口内）；**(3) 个体基线**（当前值对比自身历史 ≥5 个样本的中位数）。去重 = 7 天窗口 + 严重度穿透。单位闸门：记录归一化单位 ≠ 字典单位时跳过（避免跨单位误报）。区间型记录被排除在趋势/基线之外。告警**结构化存储**（`metricType`/`direction`/`valueText`/`refText`/`spanText`）+ 中文文本兜底，展示时按当前语言渲染。

### 4.4 用药提醒
现在是**真正按时刻触发**：`MedicationAlarmScheduler` 用 `AlarmManager.setExactAndAllowWhileIdle`（无精确闹钟权限时降级为近似），每个 (提醒, 时刻) 一个闹钟，由 `MedicationAlarmReceiver` 在触发时以及开机/时区变更/改时间/应用更新时重新排期。日历导出写入每日事件 + 提前 5 分钟提醒，并用稳定的 `[homehealth:med:<id>]` 标记保证清理幂等；编辑/启停/删除都会同步日历事件，且带孤儿保护。

## 五、数据模型与迁移

7 个实体：`family_members`、`health_records`、`medical_documents`、`alerts`、`medication_reminders`、`qa_history`、`llm_call_logs`。

- **v1→v10 全部手写迁移**；**刻意不使用 `fallbackToDestructiveMigration()`**——版本跳变时宁可启动失败，也不静默清空健康数据。
- v4→v10 的迁移 SQL 集中在 `AppMigrationSql`，并**与 JVM 测试共用同一份**，使 DDL 不会与已入库的 schema（`app/schemas/…/4.json`…`10.json`）悄悄漂移。
- 值得注意的建模：`health_records.comparator`（`<0.1` / `>100` 的 LT/GT）；`alerts` 7 个结构化列；`qa_history.imagePath`；`medical_documents.rawText` + `normalizationNotesJson`；`family_members` 8 个健康档案列（v10）。
- 用 `@Upsert` 替代 `INSERT OR REPLACE`，避免 SQLite REPLACE 的「先删后插」触发外键级联删除。

## 六、LLM 集成层

- **双协议**：OpenAI 兼容 `chat/completions` 与原生 **Anthropic Messages API**（system 独立传参、base64 图片 `source`、`anthropic-version` 头、扩展思考的 temperature=1 降级）。
- **非对称流式**：问答走 SSE 流式；报告解析保持单次请求-响应（需要完整 JSON）。
- **重试策略**：指数退避 + 抖动，仅限 429 / 5xx / IO；流式只在**首个增量到达前**重试（已部分上屏时重发会造成重复）。
- **取消**：非流式（`executeCancellable`）与流式都会在协程取消时取消在飞的 OkHttp `Call`。
- **视觉/文本严格分离**：解析必须用视觉模型，文本模型会被运行时拒绝并给出可操作提示。带图提问会解析视觉路由（问答供应商 → 解析服务兜底），并在回答来源里如实标注。
- **可观测性**：每次调用把供应商/模型/场景/耗时/提示与补全字符数/重试次数/失败类型写入 `llm_call_logs`——**绝不记录提示词与回复内容**（那里面是健康数据）。
- **Agent 网关**：`ReActAgent` 用文本模型；图片只经 `read_report_image` 工具送往视觉模型（User 条目不带内联图片），与设计文档一致。

## 七、隐私与安全

- `android:allowBackup="false"`——关闭 `adb backup` / 云备份导出通道。
- API Key 经 **Android Keystore AES-256-GCM** 加密（每次随机 IV，密钥材料不出 TEE）；历史明文 Key 就地迁移；解不开的 Key 会被标记为独立状态，而不是显示「未填写」。
- **版本化首启同意**（`CONSENT_VERSION_CURRENT`）把关整个界面与权限申请。
- FileProvider 未导出；图片写入做路径校验；ProGuard/R8 keep 规则覆盖 Gson DTO、Room 实体、Hilt、WorkManager。
- 数据只在用户主动操作时离开设备，且**直连用户自己配置的供应商**、用用户自己的 Key。

## 九、亮点

1. **连贯、成熟的架构**——清晰分层、Hilt、迁移 SQL 单一事实来源、刻意不做破坏性迁移。
2. **真正用心的 LLM 工程**——双协议、非对称流式、取消、受限重试、以及不复制敏感数据的可观测性。
3. **站得住脚的隐私姿态**——两层独立防线（关闭备份 + Keystore 加密）、版本化同意、无开发者服务器。
4. **归一化 + 检测叙事一致**——别名/单位/换算字典在检索、问答上下文、异常检测之间复用；区间值保守处理。
5. **出色的内联文档**——几乎每个非显然的决策都带「为什么」注释（代码库读起来像工程决策记录，而非只有实现）。
6. **双语产品面完整**——381/381 字符串 key 对齐，含通知与日历事件。

## 十、现存缺口、风险与建议（按优先级）

**P1 —— 建议尽快修**
1. **文档/代码漂移（见 §11）**。README 与部分注释仍描述 DB v9；代码已是 v10。更新迁移表与版本引用。
2. **Agent 的「依据与模型所见逐字一致」并不严格成立**。`ReActAgent` 把**完整**工具文本并入 `evidence`，而模型收到的是被截断的 observation（`OBSERVATION_CHAR_BUDGET = 1500`）。截断触发时，用户的「数据依据」块可能比模型看到的多，与 `buildAgentReferences` 的注释矛盾。建议同样截断 evidence（或加标注）。
3. **旋转屏幕会重复弹通知权限框**。`MainActivity.RequestNotificationPermissionOnce` 的 `requested` 标记用的是 `remember`（非 `rememberSaveable`）。

**P2 —— 打磨项**
4. **每日任务漂移**。24h `PeriodicWorkRequest` + 一次性初始延迟，在 DST/时区变更后会整体漂移；可考虑在 `TIMEZONE_CHANGED` 时重排。
5. **同意顺序边缘问题**。`HomeHealthApp.onCreate` 无条件调度每日健康检查 Worker——在同意校验之前。新装或同意版本号递增时，理论上可能在同意前收到健康预警通知。
6. **`HealthTypes.labelRes` 对未知类型仍返回 `0`**。当前所有调用点都经由安全的 `metricLabel()` 兜底，但裸函数对新调用点仍是潜在崩溃点。
7. **拍照临时文件名用 `System.currentTimeMillis()`**（`DocumentUploadViewModel.prepareCameraCapture`）；正式副本已用 UUID，但临时路径在同一毫秒内可能碰撞。
8. **测试覆盖缺口**——网络、仓库、UI。最高价值的新增是 `LlmClient` 流式/重试测试与少量 ViewModel 测试。

**路线图（README 自认）**
9. 尚无向量/混合检索（仅 BM25）——最大的 RAG 缺口。
10. 无对外暴露健康工具的 MCP Server；无端侧 LLM；无 Health Connect 集成。
11. 参考范围缺权威出处，且无年龄/孕期分层（`HealthTypes` 内已注明为待办）。

**观感项**
12. `applicationId`（`com.adajunk.homehealth`）≠ `namespace`（`com.example.homehealth`）；`com.example` 命名空间是占位风格的名称。

## 十二、总体评价

HomeHealth 是一款**架构良好、文档异常扎实的 Android 应用**，工程质量明显高于一般的个人/副业项目。它的差异化是**真实落地**的，而非宣传口号：本地优先隐私的两层独立防线、能避免跨单位误报的归一化层、保守的三规则异常引擎、刻意保留快路径而非「万事皆 Agent」的双路径问答设计，以及不复制敏感数据的 LLM 可观测性。

剩余工作主要属于**维护与深化**，而非正确性：把文档同步到 v10 schema、收紧几处小边缘（依据截断对齐、同意顺序、权限标记持久化）、把测试覆盖扩展到纯逻辑之外，并按项目自身路线图补上向量/混合检索，完成 RAG 叙事的最后一块。
