# Embedding 可行性与必要性评估

> 评估日期：2026-09-16 ｜ 代码基线：`main @ cf51156`（SSE 流式 + ReAct 已提交）
> 范围：健康问答链路（`QaRetriever` BM25 检索 + `ReActAgent` 工具环 + 报告解析入库）
> 关联：`docs/项目深度分析报告-v3-考纲映射.md` 列出的唯一剩余技术缺口「向量库选型」

---

## 0. 结论

问的是两个问题，答案相反：

| 问题 | 结论 | 一句话依据 |
|---|---|---|
| 用 embedding 补充 / 替换**结构化指标记录**的检索 | **不必要**（现阶段） | 语料是「小规模 + 闭词表 + 短查询」，BM25 已接近该场景上限；而语义泛化这一块**已经由 LLM 承担了**（ReAct 路径），价值重叠 |
| 用 embedding 检索**报告叙述文本**（结论 / 印象 / 建议 / 医生意见） | **必要，但前提是先让这类文本存在** | 走读发现 `ParseResult.rawText` **从不落库**（§1.3）——现在上向量库，索引的是一个空语料 |

**一句话**：当前瓶颈不是"检索算法不够语义"，而是**叙述性内容根本没进语料**。顺序错了，先补语料，再谈算法。

---

## 1. 必要性

### 1.1 结构化记录：不必要，而且理由是架构性的

先看这个检索问题实际上有多小：

| 维度 | 实际情况 | 出处 |
|---|---|---|
| 语料来源 | 单个成员的**全部数值记录**（`getAllByMember(memberId)`） | `QaRetriever.index` 调用处 |
| 单条文档文本 | 指标名 + 全部别名 + 类型键 + 数值 + 单位 + 比较符语义 + 日期 + 备注 ≈ 15–40 字 | `QaRetriever.documentText` |
| 切分后 term 数 | 约 20–60（中文按单字 + 相邻双字） | `QaRetriever.tokenize` |
| 词表 | **封闭**：49 项指标 / 106 条别名 / 24 条单位写法 | `HealthTypes` + `SchemaNormalizer` |
| 记录量级 | 个人自用，单成员 10² ~ 10³ 条 | 场景推断 |
| 查询形态 | 10–20 字短问句，且**必须命中强指标词才走检索** | `QaRetriever.strongTermsOf` 闸门 |

TF-IDF 系（BM25）在千级文档下的统计量足够稳，这是它的舒适区。而"同义改写"这个 BM25 的经典软肋，在这里**已经被两道前置机制消掉了大半**：

1. **别名表**（106 条）在索引时把口语说法写进文档文本（`ALIASES_BY_TYPE`），让「LDL 多少」「维D 够不够」能命中；
2. **成组词表**（`GROUP_KEYWORDS`，10 组）把「血脂」「肝功能」「肾功能」「甲状腺」「血常规」「电解质」「维生素」这类器官/套餐级说法命中后展开为多项。

### 1.2 但更关键的是：语义泛化这块，LLM 已经接管了

这是这次评估里最要紧的一条判断。

`STRONG_VOCAB` 里只有指标名、别名、成组词。像「肝好不好」「肾有没有问题」这种**单字器官说法**，既不在指标词表里，也不在成组词表里，因此 `strongTermsOf` 返回空集 —— 按第 8 轮定下的路由规则，这类问题**走 Agent 路径**，由 `ReActAgent` 的循环让模型自己决定去调 `search_records` / `get_alerts` / `get_reference_range`。

也就是说：**「把用户的口语说法映射到该查哪些指标」这件事，已经由 LLM 在做**——而且 LLM 本来就是目前最强的语义映射器，比一个 24M 参数的向量模型更准确、更有解释力（它会把"我打算查 ALT/AST"写在 Thought 里，向量检索给不出这个）。

**所以在这个项目里，embedding 的"语义泛化"价值与 LLM 的价值高度重叠，而 LLM 已经在链路上。** 这是"不必要"的核心理由——不是"语料小所以不需要"，而是"这项能力已经有更好的实现"。

### 1.3 真正的空洞：叙述性内容从不落库

这是本轮走读翻出来的事实，不是推测。

**证据链：**

1. `LlmClient` 解析报告时返回 `ParseResult(records, rawText)`，其中 `rawText = content.text.trim()` —— 即模型对报告的**完整转录文本**，提示词里明确要求「单独列出「结论」「印象」「建议」这类结论性文字，原文照录，不要改写」。
2. 这份文本的**唯一去向**是 `DocumentUploadViewModel.rawText` → 确认页展示给用户核对。
3. 落库时（`DocumentRepositoryImpl.confirmRecords`）只写 `extractedJson = gson.toJson(records)` —— **纯数值记录**。
4. ⇒ **用户一离开确认页，报告的叙述性内容就永久消失。**
5. `read_report_image` 工具同理：读图结果作为 observation 回填给模型，**不落库**；下一轮再问「上次那份报告怎么说」已无从查起。

后果：**影像报告、病理报告、出院小结这类本来就无法结构化的内容，当前是"读一次、丢一次"。** 用户第 1 条需求（QAScreen 支持发图）解决的是"这一次能问"，没有解决"以后还能问"。

这件事比"要不要上向量库"重要得多，而且它**不是检索算法问题**：内容没进语料，换什么检索器都检索不到。BM25 检索不到、embedding 也检索不到。

### 1.4 一旦语料补上，结论会反转

把报告原文纳入语料之后，BM25 的适用前提才会真正破裂：

| 语料形态 | 词表 | 查询形态 | 适配算法 |
|---|---|---|---|
| 数值记录（现状） | 封闭（49 指标 / 106 别名） | 短问句，含已知指标词 | BM25 ✅ |
| + 报告原文（建议补） | **开放**（医学叙述文本，几乎无界） | 自然语言长句，「上次那份报告说我肝有问题吗」 | BM25 ⚠️ 词表覆盖不住 → **此时 embedding 才有正当性** |

所以 embedding 的引入时机是 **"报告原文进语料"之后**，不是之前。

## 2. 可行性

### 2.1 三条路线

| | 端侧 ONNX（bge-small-zh-v1.5） | 云端 Embedding API | 不做产品化，只做对照实验 |
|---|---|---|---|
| 隐私 | 全本地，与「无开发者服务器」一致 | **需全量上传历史记录** | 无影响（离线数据集） |
| 性质差异 | — | 与"按需提问时才上传当前问题涉及的记录"不同：建索引等于**把从未问过的记录也全部送出去** | — |
| 离线可用 | ✅ | ❌ | — |
| APK 体积 | INT8 约 **23–25MB**；FP16 约 60MB；FP32 约 90–120MB（含词表） | 0 | 0 |
| 建索引耗时 | int8 单条约 5–30ms（视机型）→ **1000 条要 5–30s，不能每次提问重建，必须持久化** | 一次批量请求（有上限） | 毫秒级 |
| 存储 | 1000 条 × 512 维 × 4B ≈ **2MB**，BLOB 存 Room 即可 | 同 | — |
| 检索 | 暴力余弦：1000 × 512 ≈ 50 万次乘加，< 1ms | 同 | — |
| 持续成本 | 0 | 按 token 计费 + 需要第二套 Key/额度 | 0 |
| Schema | **需要 Room v9**（存向量） | 同 | 无 |

> 模型参数（外部公开数据，非本项目实测）：`BAAI/bge-small-zh-v1.5`，512 维、约 24M 参数、词表 21128、C-MTEB 中文基准均分 57.82；BERT 架构，**取 CLS 向量**并做 L2 归一化（用错池化方式会让相似度分布坏掉）。ONNX 导出版本现成，`onnxruntime-android` 走 NNAPI 可拿到硬件加速。

### 2.2 若要做端侧，技术清单

1. **模型**：`bge-small-zh-v1.5` 的 ONNX INT8 版（体积与精度性价比最好，INT8 相对 FP32 的 C-MTEB 损失约 2%）
2. **Tokenizer**：这是最容易低估的一块。BERT WordPiece，中文词表 21128 基本是 **char-level**，因此**可以手写一个最小 WordPiece**（最长匹配 + `##` 前缀），避免引入 Rust tokenizers 的 JNI。但**必须与模型词表严格对齐**
3. **运行时**：`onnxruntime-android`（NNAPI / XNNPACK EP）
4. **持久化**：`FloatArray` → `ByteBuffer` → BLOB 存 Room。**注意语料规模决定了不需要向量数据库**——1000～10000 条向量的暴力检索在毫秒级，引入 FAISS/Milvus 是过度设计
5. **融合**：BM25 与向量用 **RRF**（`score = Σ 1/(k + rank)`，k 取 60）而非分数加权——两路分数量纲不同，加权需要调参且不稳；RRF 只用排名，鲁棒
6. **查询前缀**：BGE 系列检索场景建议给 query 加指令前缀（v1.5 之后可选但有效）；文档侧不加
7. **加载策略**：懒加载 + 推理会话复用；模型加载约 0.3–1s，首启不适合阻塞主流程

### 2.3 成本与风险

| 项 | 评估 |
|---|---|
| 工作量 | 模型接入 + tokenizer + 持久化迁移 + RRF 融合 + 评估 ≈ **2–3 天**（其中 tokenizer 对齐最可能超时） |
| 主要工程风险 | **Android 端 tokenizer 与模型词表不一致** → 建议验收标准：同一条文本，Python 端与 Android 端向量的余弦相似度 > 0.999 |
| 效果风险 | bge-small-zh 在**通用中文**上强，但"体检指标术语"属长尾；实际表示质量必须实测，不能假设 |
| 产品风险 | APK +25MB；若走云端则破坏「无开发者服务器」叙事 |
| 迁移风险 | 需要 Room v9，按项目纪律（构建两次、当天不装半成品包）安排 |

## 3. 建议的执行顺序

**Step 0（先做，性价比最高，零模型）**
1. 把报告叙述文本落库：`medical_documents` 增 `rawText`（或另建 `document_texts` 表）——**Room v9**
2. 把落库的文本纳入检索语料（`QaRetriever` 的 index 输入从"仅记录"扩展为"记录 + 报告原文"）
3. `read_report_image` 的读取结果可选落库（或至少明确告知用户"未保存"）

→ 收益：报告结论以后还能问到，补上 §1.3 最大的空洞。**这一步的面试价值高于向量库**：可以讲"我先定位到检索不到是因为内容没存，不是算法不行"——这是判断力，不是技术堆料。

**Step 1（Python 对照实验，1 天内）**
在同一批中文健康查询上对比 **BM25 / bge-small-zh 向量 / RRF 混合**，产出 Recall@5 与 MRR 表。查询集建议覆盖四类：指向指标 / 器官级 / 症状级 / 报告叙述。
→ 两个收益：① 把"向量库选型"从"我刻意不用"变成"我用数据比过"；② 考纲的手撕题与资料基本是 Python 生态，这一步顺带补语言错配。

**Step 2（可选，把结论搬进 App）**
若 Step 1 显示混合明显更优，再按 §2.2 落地端侧。**此时 Step 0 已经把语料准备好了，向量才有东西可索引。**

**明确不建议**：现在直接接云端 Embedding API。理由不是技术不行，而是：① 建索引意味着全量上传历史记录，与"无开发者服务器 + 按需提问"的叙事冲突；② 在 Step 0 之前，索引的是一个闭词表结构化语料，收益接近 0，却要搭上一次 schema 迁移和一笔持续成本。

## 4. 面试话术：「你选了什么向量库 / 为什么」

四段式，控制在 60 秒内：

1. **先说边界**：我的问答是闭词表检索——49 个指标 + 106 条别名 + 10 组成组词，加上强指标词闸门，查询必须命中已知指标词才走检索。BM25 在这个语料上接近上限。
2. **再说架构理由**（这段最值钱）：语义泛化这块我没有交给向量，而是交给 LLM——泛化问题走 ReAct 路径，由模型自己决定查哪些指标。**LLM 本身就是最强的语义映射器，而且它会把推理写在 Thought 里，比向量召回更可解释。** 在有 LLM 的 RAG 里，embedding 的必要性要看"能不能让 LLM 直接决定检索什么"——我的链路已经这么做了。
3. **再说什么时候会换**：当叙述性文本进语料（报告结论、影像描述）——词表不再封闭、查询会变成自然语言长句。这条路径我想清了：端侧 bge-small-zh + 手写 BERT WordPiece + RRF 融合 + 向量持久化；并且因为语料只有千级，**不需要向量数据库**，暴力余弦就够。
4. **收尾给数据**：我在 Python 里做过 BM25 / 向量 / 混合的对照，Recall@5 是 X vs Y vs Z。（Step 1 的产出）

第 2 段是这套回答与"我用了 FAISS"的分水岭：前者是选型判断，后者是技术堆料。
