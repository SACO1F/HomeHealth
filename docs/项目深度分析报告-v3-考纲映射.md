### 阶段 2 · Agent 核心范式 + RAG 进阶

| 考点 | 覆盖 | 落点与讲法 |
|---|---|---|
| **手写 ReAct** | 🆕 ✅ | `ReActAgent` 是手写循环（`for (turnIndex in 1..MAX_TURNS)`），没有框架。可讲的点：终止条件、最后一轮撤工具、工具失败注入、正文与思考的分流 |
| Plan-and-Solve | ❌ | 没有。**要备"为什么不需要"**：本项目的问题形态是"先看数据再决定下一步"，没有"先写完整计划"的必要；且计划一旦写死就失去了 Agent 适应数据的能力 |
| Reflection | ⚠️ 轻量 | 只做了"observations 全空时不允许下结论"（防模型在无数据时编建议）。考纲写的是"手写 Reflection"，这是明确缺口 |
| 记忆与上下文工程 | ✅✅ | 四层预算：检索 Top-K=12 → 每指标 Top-10 → 摘要 6000 字符 → **单个 observation 1500 字符**；加上"单位不一致时跳过高低标注"的防污染。**新增**：工具轮正文并入思考轨迹，不污染答案 |
| Advanced RAG 优化 | ⚠️ 一半 | 有 Pre-Retrieval 的自适应路由（强指标词闸门 = query routing），且有**两级路由**（快路径 / Agent）。没有：Hybrid、Rerank、Query Rewrite、Multi-hop |
| 向量库选型 | ⚠️ 反向 | 零 embedding。**必须能把"为什么不选"讲成一次主动决策**：语料千条内、中文指标是强关键词场景、云端 Embedding 破坏"数据不上传"承诺、内存索引避免再开一次 DB 迁移。再答"什么条件下会切换" |

## 二、本轮改动带来的新可讲素材（按"值钱程度"排序）

### 1. 工具必须只读 —— 最值钱的一条

`DetectAnomaliesUseCase.invoke()` 会**写库**：`createAlert` + 7 天去重窗口 + 严重度穿透 + 可能触发系统通知。如果按"把 4 个模块包一层"的直觉做法直接把它当工具：

> 用户只是问一句「我有什么异常吗」，系统就凭空生成一批告警进预警页 —— 这是**用查询的姿势触发了写操作**。

所以工具是 `get_alerts`（读已判定结果），检测仍由每日后台任务与录入流程负责。这条比"我实现了 ReAct"更能证明工程判断力，因为它是**只有真读过代码才会发现**的问题。

### 2. 用 Agent 替换整条链路是负优化

实测推演：指向具体指标的问题（"最近血糖怎么样"）快路径 1 次 LLM 请求，Agent 路径 2 次——**延迟翻倍而质量不变**。所以做的是路由，不是替换：

```
命中强指标词 → 快路径（BM25 → 1 次请求 → 逐字上屏）
未命中       → Agent 路径（ReAct ≤5 轮）
```

路由条件直接复用了当初为修「弱字窄化」bug 引入的 `strongTermsOf` 闸门——一个已有机制被赋予了新职责，而不是新增一层判断。

### 3. 流式 function calling 的分片累积

两家协议的调用参数都是**分片**返回的，看到一段就当完整 JSON 解析必然出错：

- OpenAI：`delta.tool_calls[]` 按 `index` 分组，`arguments` 是逐片拼接的字符串
- Anthropic：`content_block_start` 给一次 id / name，之后全是 `input_json_delta.partial_json`

`ToolCallAssembler` 累积到流结束才产出调用。这是流式 function calling 最容易写错的地方，也是很好的追问靶子（见第三节）。

### 4. 最后一轮撤掉工具声明

与其在轮数用尽时拿着一堆**未被回填**的工具调用收场，不如提前把工具声明去掉，逼模型用已有证据作答。这样"轮数用尽"和"正常收尾"走**同一条代码路径**，不会出现"没有回答"的空档。

### 5. 怎么测一个 Agent 循环

把"LLM 决策"抽成 `AgentLlmGateway` 接口，循环本体就能用假网关脚本化：

| 测试 | 覆盖的策略 |
|---|---|
| 两轮收敛 | 工具调用 → 回答的事件序列 |
| 最后一轮不含工具 | 轮数护栏 |
| 工具轮正文不进 Answer | 正文与思考的分流 |
| 工具抛异常 | 失败转为观测、循环继续 |
| 同一工具连续失败 2 次 | 禁用机制 |
| 无证据即抛出 | 交给上层降级 |
| observation 超预算 | 截断与标注 |

这套测试本身就是加分项：**Agent 的难点全在"什么时候该停、失败了怎么办"，而这些分支靠真机验证要凑齐网络超时、供应商抽风、模型乱调工具等场景，成本高且不可复现。**

### 6. 发图提问的模型路由

问答服务配的是**文本**模型，图片必须走**视觉**模型。三档回退：问答模型本身支持 → 直接用；否则回退「报告解析服务」并**在来源里如实标注**；都没有 → 明确引导文案。**绝不静默把图丢掉**——让用户以为模型看过图了，在健康场景里代价很高。

### 7. 护栏是设计的一部分

`AgentConfig.kt` 里 5 个数字，每个对应一种具体的失控方式：轮数 5（成本超线性增长）、工具调用 8（防单轮并行 × 多轮叠加）、观测 1500 字符（一次查询就能撑爆上下文）、连续失败 2 次禁用（模型会对着同一个错参数反复重试）、超时 10s/60s（本地工具 vs 网络请求）。

## 三、本轮新引入的追问点（必须提前准备）

这些是面试官**顺着新代码往下问**时最可能命中的地方。答不上来会显得"功能是抄的"。

| # | 追问 | 回答骨架 |
|---|---|---|
| 1 | 你的 ReAct 循环怎么保证会停？ | 三重：`MAX_TURNS=5` 硬上限；**最后一轮不提供工具**，模型只能作答；工具调用总数上限 8。加上"轮数用尽也不报错，用已有证据收尾" |
| 2 | 模型调用工具传错参数怎么办？ | `ToolArgs` 容错解析（缺字段/类型不符返回 null 而非抛异常）+ 参数错作为**失败观测**回填给模型让它自我修正 + 同一工具连续失败 2 次即禁用（防止反复撞同一面墙） |
| 3 | 为什么工具结果要截断？ | 一次 `search_records` 返回多项 × 多条就能把上下文撑爆；预算 1500 字符，且截断时**明确标注省略了多少**（模型需要知道"还有更多"） |
| 4 | OpenAI 和 Anthropic 的工具调用有什么不一样？ | 声明字段名（`parameters` vs `input_schema`）、流式分片形态、回填结构（`role:"tool"` vs user 消息里的 `tool_result` 块）、system 落在哪 |
| 5 | 流式 function calling 最容易错在哪？ | 参数是分片字符串，**必须按 index 累积到流结束**才是合法 JSON；我为此单独写了 `ToolCallAssembler` 并加了单测 |
| 6 | 为什么 Agent 的最终回答不逐字上屏？ | 只有一轮结束后才知道它是不是最终回答。中间轮的推理先流到答案区、发现是工具轮再撤回，对用户是明显抖动。牺牲流式换正确性，快路径仍逐字上屏 |
| 7 | Agent 和快路径怎么选？ | `QaRetriever.strongTermsOf` 抽不到强指标词 → 泛化/多步问题 → Agent。并说明**为什么不全局上 Agent**（负优化） |
| 8 | 发图提问时问答模型不支持图片怎么办？ | 三档回退 + 来源如实标注；绝不静默丢弃图片 |
| 9 | 为什么数据库又升了一版？ | `qa_history.imagePath` 承载叙述性报告的附图；迁移纪律：导出 schema 快照 + JVM 结构级测试 + androidTest 真机校验 + 刻意不用破坏性迁移兜底 |
| 10 | 多轮 Agent 的成本和可靠性怎么算？ | token 随轮数**超线性**（每轮重发工具 schema + 全部历史 observation）；可靠性也是叠加的（4 轮 × 99% ≈ 96%）。所以有降级矩阵：任何一环失败都要能给出"已获取部分的答案" |
| 11 | 为什么读图要做成工具，不直接内联图片？ | 单轮场景内联更省（1 次请求）；但 ReAct 多轮下 base64 会**随每轮重发**，工具形式把图片一次转文本，后续轮次保持纯文本。判断随场景变 |
| 12 | 为什么没有用 Reflection？ | 只做了"观测全空不允许下结论"的轻量保护。完整 Reflection 要一次额外请求，在 5 轮预算内会挤掉工具调用轮；**承认这是取舍，不是遗漏**，并说清什么条件下值得加 |

## 五、STAR 话术 v3

**30 秒版（已更新）**

> HomeHealth 是本地优先的 Android 家庭健康管家。拍照上传体检报告后，Vision 大模型以 JSON 模式抽取 49 类健康指标，经 Schema 归一化层（106 条别名映射、24 类医学换算、无可靠系数绝不猜测）再人工确认入库。问答链路是**双路径**：指向具体指标的问题走 BM25 检索 + 引用溯源，泛化问题交给一个**手写的 ReAct Agent**——4 个只读健康数据工具（检索记录 / 参考范围 / 已判定告警 / 读报告图片），最多 5 轮，带完整护栏与降级。回答走 SSE 流式，先给数据依据再给结论，每个数字都能追溯到具体记录。接 7 家供应商、双协议（含 Anthropic Messages 的原生工具调用），每次调用都有本地可观测日志。

**2 分钟 STAR 的 A 段（挑这三个讲）**

1. **工具只读**：`DetectAnomaliesUseCase` 会写库，直接包成工具等于"问一句话就凭空多出告警"——工具读已判定结果，检测交给确定性代码。**医疗场景让确定性系统做确定性判断。**
2. **路由而非替换**：实测下指向具体指标的问题用 Agent 是负优化，所以保留快路径、只对泛化问题启用 Agent。
3. **可测的 Agent**：把 LLM 决策抽成接口，用假网关把"轮数用尽""连续失败""观测截断"这些策略脚本化——Agent 的难点全在这些分支上。

**高频追问预案（v3 增量）**：见第三节 12 条。

## 六、诚实提醒：两个真实风险

### 1. 三条新路径都没上过真机

流式问答、Agent 工具调用、随提问附图**全部只跑过 JVM 单测与编译**。Room 已升到 v8，装机时必须遵守既有纪律：**升版本后构建两次**、核对 androidTest 内 schema 列表含 `8.json`、**当天不要装中途构建的半成品包**（会把 DB 版本烧到新号但列不全，之后任何新包都无法迁移）。

面试前务必装机跑一遍，重点看：跨网络中断、切页取消、发图后模型来源标注、Agent 路径的工具轨迹展示。

### 2. 代码面变大 → 可被追问的面也变大

本轮新增 10 个 main 文件。**下面这些必须能逐行解释**，否则宁可不主动提：

| 文件 | 必须讲清的 |
|---|---|
| `ReActAgent.kt` | 循环结构、最后一轮撤工具、正文/思考分流、降级出口 |
| `AgentRequestBody.kt` | 双协议翻译的四条差异（声明 / 调用 / 回填 / system） |
| `LlmStreamParser.kt` | 两个 `parse*` 的分派 + `ToolCallAssembler` 的分片累积 |
| `HealthTool.kt` | 契约、`ToolArgs` 容错、为什么成员信息不进工具参数（模型会选错人） |
| `AgentConfig.kt` | 5 个数字各自对应哪种失控方式 |
