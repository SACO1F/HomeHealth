## 一、结论摘要

- **P1（应尽快修）：9 项**——其中 2 项是"宣传与实现不符"级别（用药提醒从不按用户时刻触发；Agent 带图发给文本模型），
  1 项是可由 LLM 畸形输出直接触发的崩溃（`stringResource(0)`），2 项数据完整性（重复入库、孤儿日历），
  2 项资源/线程问题，1 项已知能力空洞（C1 rawText 不落库，确认仍在），1 项双语硬伤（通知硬编码中文）。
- **P2（择机修）：约 20 项**，集中在异常检测的边界语义、i18n 漏网、Compose 状态恢复、单位归一化的 ASCII 变体。
- **已知且仍成立的缺口**：ParseResult.rawText / normalizationNote 不落库（C1）；真机验证；向量检索对照实验（README Roadmap 自认）。

## 二、P1 缺陷清单

### P1-1 未知指标类型 → `stringResource(0)` 崩溃 ⚡唯一可稳定复现的崩溃
- `util/HealthTypes.kt:269` `else -> 0`；`SchemaNormalizer.kt:179-182` 允许未知类型原名透传入库；
  UI 多处直接 `stringResource(HealthTypes.labelRes(record.type))` 无兜底：
  - `ui/screens/documentupload/DocumentUploadScreen.kt:378`
  - `ui/screens/memberdetail/MemberDetailScreen.kt:280,323`
  - `ui/screens/familylist/FamilyListScreen.kt:207`
  - `ui/screens/recorddetail/RecordDetailScreen.kt:61`
  - `ui/components/RecordInputDialog.kt:86-87,99`
- LLM 返回自由文本指标名（如 "ALT/AST"）即触发 `Resources$NotFoundException`。
- **修法**：仿 `util/AlertText.kt:29` 的 `if (resId == 0)` 兜底，集中封装 `@Composable fun metricLabel(type)`。
- 附带：`ui/navigation/NavGraph.kt:51,55` 把 type 放 path 段，含 `/` 的类型连路由都匹配不上。

### P1-2 用药提醒从不按用户设定时刻触发
- `worker/DailyCheckWorker.kt:30-35`：`getActive()` 全量遍历逐条 `showMedicationReminder`，完全不读 `reminder.dailyTimes()`；
  `HomeHealthApp.kt:47` 唯一调度是 24h 周期任务（约 8:00 对齐一次）。
- 后果：设 20:00 的药，8:00 收到通知；真按时刻提醒只剩"手动写入系统日历"一条路。
- 与 README 宣传（"medication reminders synced with the system calendar"）存在差距——日历是手动可选，App 内提醒形同虚设。
- **修法**：逐时刻 `OneTimeWorkRequest` 链式重排或 `AlarmManager.setExactAndAllowWhileIdle` + 时区变更监听。

### P1-3 Agent 带图：图片内联发给文本模型，且每轮重发
- `LlmClient.kt:964` Agent 的 `turn()` 用 `resolveConfig(vision = false)`（排除视觉校验）；
  `ReActAgent.kt:49` 把 `context.imageBase64` 原样放进 User 条目；
  `AgentRequestBody.kt:76-87` 翻译成 `image_url` 内容。
- 后果：问答模型是纯文本、视觉靠解析服务兜底时（`QARepositoryImpl.kt:110` 允许此场景），多模态请求发给文本模型 → 400 → 整次问答降级本地引擎。
  同时与 `ReadReportImageTool.kt:9-13` 的设计声明（"工具把图片一次转成文本，后续轮次上下文保持纯文本"）直接矛盾——图片实际每轮重发，成本 × MAX_TURNS。
- **修法**：Agent 路径 `imageBase64` 置 null（只留 `read_report_image` 工具），或带图时改走 `resolveVisionConfig()`。

### P1-4 `confirmRecords` 两步写无事务 → 同一报告重复入库
- `data/repository/DocumentRepositoryImpl.kt:144-153`：`insertAll` 与 `update(COMPLETED)` 独立执行；
  中途被杀 → 文档回 `FAILED`（`resetStuckProcessing()` 172-183）→ 重试时因 `health_records` 无
  `(memberId,type,recordDate)` 唯一约束，同一报告指标重复入库 + 重复告警。
- **修法**：`androidx.room.withTransaction(db)` 包裹两步（文件/日历清理留在事务外的现有顺序是对的）。

### P1-5 编辑用药提醒 → 日历孤儿事件每日重复
- `ui/screens/reminders/RemindersViewModel.kt:43-67`：编辑只 `upsert`，不清理旧日历事件；
  删除签名用当前药名（`RemindersScreen.kt:314-319` → `CalendarEventHelper.kt:136` `"服药：$medicationName"`），
  改名后旧「服药：旧名」事件永远匹配不到、永远删不掉。
- **修法**：编辑路径先按旧 `calendarEventIds`/旧签名删事件，或改名时清空 `calendarEventIds` 并提示重写。

### P1-6 通知文案硬编码中文，双语在推送层失效
- `worker/NotificationHelper.kt:67,70,86-87`（"用药提醒：…"、"检测到 N 条…"、"每日"）、
  `util/CalendarEventHelper.kt:52,71,74`（"服药："、"来自家庭健康管家"）、
  `domain/usecase/DetectAnomaliesUseCase.kt:241,262`（`spanText` 存中文成品"近 N 天"，经 `AlertText.kt:79-81` 拼进英文模板）。
- 英文用户收到的推送/日历/趋势告警是中文或中英混杂。**修法**：全部走 `context.getString(R.string.*)`；
  日历签名与 i18n 解耦（签名改用稳定的英文标记）。

### P1-7 非流式 LLM 路径无取消传播
- `LlmClient.kt:407` `execute()` 无取消钩子（流式路径在 796-798 有 `invokeOnCompletion → cancel()`）。
- 后果：退出解析页后线程阻塞至 readTimeout(120s)；`ReActAgent.kt:133` 的工具超时判"超时"后底层请求仍在跑满 120s。
- **修法**：非流式路径照抄流式的取消钩子。

### P1-8 rawText / normalizationNote 不落库（已知 C1，确认仍在）
- `data/remote/ParseResult.kt:8` 的 `rawText` 只到 UI（`DocumentUploadViewModel.kt:240`）；
  落库只存 `extractedJson = gson.toJson(records)`（`DocumentRepositoryImpl.kt:149`）；
  `EditableRecord.normalizationNote` 同样丢失。
- 后果：无法审计"模型看到什么/漏了什么"，找回漏提取指标只能重调付费视觉 API。
- **修法**：Room v9 给 `medical_documents` 加 `raw_text` 列（配合渐进迁移），或至少存归一化摘要。

### P1-9 `unreadableKeys` 非线程安全 + `DateUtils` 共享 SimpleDateFormat
- `data/SettingsPrefs.kt:109,128,134,137,150,159`：HashSet 在 IO 流内被 `readSecret` 读写，无同步；
- `util/DateUtils.kt:11-14`：共享 `SimpleDateFormat` 被 WorkManager 线程与 UI 线程并发调用，
  错乱日期会写进告警文案与问答上下文。
- **修法**：前者换 `java.util.concurrent.ConcurrentHashMap.newKeySet()`；后者每次新建或换 `java.time`。

## 四、功能改进建议（对照 README 功能承诺）

按"宣传与实现差距"排序，前 5 项对面试叙事影响最大：

1. **用药提醒做成真提醒**（P1-2 + P1-5 + P2-16 一起修）：README 只承诺"日历同步"，实际做上"App 内按时刻提醒 + 日历导出幂等"，比现在"8:00 广播一遍"强一个档次；也是面试里"WorkManager vs AlarmManager 取舍"的好素材。
2. **rawText 落库（C1）**：这是"可审计性"叙事的最后一块——模型原始输出、归一化痕迹都可回放，配合 llm_call_logs 就是完整的可观测闭环。
3. **Agent 视觉路径二选一**（P1-3）：要么"图片只在工具里转文本"（现设计声明），要么"带图走视觉模型"（实际代码）——两者都成立，矛盾不成立。
4. **告警可信度三补丁**（P2-1/2/4：单位闸门、区间值过滤、ASCII 单位变体）：异常检测是这个 app 的核心卖点，三个边界语义补上后"三条规则"的叙事就无懈可击。
5. **非流式取消 + evidence 对齐**（P1-7 + P2-8）：都是小改动，换来协程取消与"逐字一致"两个承诺的闭环。
6. 通知/日历 i18n 全量收口（P1-6）：工作量小，消除"双语"宣传的最后一处硬伤。
7. 长线（README Roadmap 已自认）：向量检索对照实验（bge-small-zh-v1.5 + RRF）、真机验证、Reflection 完整版。

## 五、已核对无问题的面（抽样结论）

- Room：迁移 SQL 与 4→8 schema 逐字一致、无 fallbackToDestructive、实体无漂移、@Upsert 避开 REPLACE 级联坑。
- 协程：无 GlobalScope/runBlocking/Main 误用；QA 流式 flowOn(IO) 正确；CancellationException 原样重抛。
- SecretStore：IV 随机不重用、GCM 128 位 tag、密钥不出 Keystore、日志只记异常类型；git 近 30 commit 无明文 key。
- SSE 基础：多字节 UTF-8 跨分片安全、CRLF/LF 兼容、[DONE]/message_stop 正确终止、首个增量后不重试防重复上屏。
- 首启同意（新功能）：权限/主界面全在 `if (consented)` 内、返回键即退出、版本比较逻辑正确、旋转/进程重建状态一致；仅 P2-17 的"同意前已调度 Worker"一个边缘。
- i18n 键集：中英 strings.xml key 集合完全一致、无重复 key；LazyColumn 均有稳定 key；collectAsStateWithLifecycle 使用正确。
- SchemaNormalizer 换算因子抽查 19 组全部方向正确，别名表无一键双映射。
- allowBackup=false、FileProvider 未导出、通知渠道/权限检查齐全。
