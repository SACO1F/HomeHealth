## 一、项目概览

**HomeHealth（家庭健康管家）** 是一款**本地优先、隐私至上的 Android 家庭健康管理应用**。

核心价值链路：**拍摄体检报告照片 → 视觉大模型以 JSON 模式提取结构化指标 → 归一化层统一指标名与单位 → 用户核对确认 → 数据落入设备本地 Room 数据库**。在此之上提供趋势图、三规则异常检测、中英双语界面、用药提醒，以及一个在「关键词检索」与「手写 ReAct Agent」之间路由的健康问答功能。

**定位判断**：这是一个**个人独立完成的、作品集 / 面试级项目**——`docs/` 目录同时包含面试准备材料（Agent 岗面试指南、100 题题库、考纲映射），这也解释了许多刻意的、可讲述的工程决策。代码内联注释异常扎实，几乎每个非显然决策都带「为什么」。

**隐私承诺（真实落地，非口号）**：所有健康数据存于设备本地 Room；应用**不经过任何属于开发者的服务器**；数据只在用户主动触发解析 / 问答时离开手机，且**直连用户自己配置的供应商**、用用户自己的 API Key 认证。不配置任何 LLM 也完全可用（内置离线问答引擎兜底）。

## 五、数据模型与迁移

**7 个实体**：`family_members`、`health_records`、`medical_documents`、`alerts`、`medication_reminders`、`qa_history`、`llm_call_logs`。

**迁移策略**：
- v1→v10 **全部手写迁移**；**刻意不使用 `fallbackToDestructiveMigration()`**——版本跳变时宁可启动失败，也不静默清空用户的健康数据。
- v4→v10 的迁移 SQL 集中在 `AppMigrationSql`，并**与 JVM 测试共用同一份**，使 DDL 不会与已入库的 schema 悄悄漂移。
- 索引名必须与 Room 生成的 `index_<table>_<column>` **逐字一致**，否则打开数据库抛 `IllegalStateException`。
- 用 `@Upsert` 替代 `INSERT OR REPLACE`：SQLite 的 REPLACE 是「先删后插」，会触发外键级联删除——这是一次真实踩坑的复盘。

**演进表**：

| 版本 | 变更 |
| --- | --- |
| v1 → v2 | `family_members.heightCm` / `weightKg` |
| v2 → v3 | `qa_history.thinking`（深度思考模型的思考过程） |
| v3 → v4 | `medication_reminders.calendarEventIds` |
| v4 → v5 | `alerts(memberId)`、`health_records(memberId, type, recordDate)` 索引 |
| v5 → v6 | `health_records.comparator`（承载 `<0.1` / `>100` 区间型结果） |
| v6 → v7 | `llm_call_logs` 表 + `alerts` 7 列结构化字段 |
| v7 → v8 | `qa_history.imagePath`（随提问附带的报告图片） |
| v8 → v9 | `medical_documents.rawText` + `normalizationNotesJson`（解析原文与归一化说明，可审计） |
| v9 → v10 | `family_members` 健康档案 8 列（血型 / 腰围 / 运动 / 饮食 / 吸烟 / 饮酒 / 慢性病史 / 手术史） |

**值得注意的建模**：`health_records.comparator`（LT/GT）；`alerts` 7 个结构化列（`metricType`/`direction`/`valueText`/`unitText`/`refText`/`spanText`/`baselineText`）；`qa_history.imagePath` + `sources` + `thinking`；`medical_documents.rawText` + `normalizationNotesJson`。

## 六、核心流程

### 6.1 报告解析（刻意非流式）

`拍照/相册 → saveImageAndCreateDocument（UUID 文件名）→ 压缩为 base64（最长边 1600px，防 OOM）→ 视觉模型 JSON 模式（temperature 0.1 / maxTokens 4096）→ parseRecordsJson（括号配平提取，容忍 ```json 包裹与前后杂文字）→ 逐条 SchemaNormalizer.normalize → 可编辑卡片（含换算标注）→ confirmRecords`。

- `confirmRecords` 用 `database.withTransaction { deleteBySourceDocument + insertAll + update(COMPLETED) }` 包裹，堵住「重复入库」漏洞。
- `rawText` 与 `normalizationNotesJson` 落库（DB v9），支持审计与回放。
- 卡在 `PROCESSING` 的僵尸文档会被重置为 `FAILED`，且带**限频 + 跳过在飞解析**两道保护。
- `DocumentUploadViewModel.parseInternal` 捕获 `Throwable`（含 `OutOfMemoryError`）→ 转为可重试失败态。
- **视觉/文本模型严格分离**：解析必须用视觉模型，纯文本模型会被运行时拦截并给出可操作提示，而不是返回一堆幻觉数据。

### 6.2 健康问答（流式，三档路由）

`QARepositoryImpl.askStream` 的事件顺序：**依据 → （工具轨迹）→ 正文 → 落库完成**。路由逻辑：

1. **快路径**——问题含**强指标词**（`QaRetriever.strongTermsOf`）→ 对成员记录做 BM25 Top-12 检索 → SSE 流式，强制 `[n]` 引用溯源。
2. **Agent 路径**——无强指标词但有数据/图片 → 手写 ReAct 循环（`ReActAgent`，≤5 轮、≤8 次工具调用），4 个只读工具。
3. **离线兜底**——未配 Key / 无记录 / 失败 → `LocalQaEngine` 规则引擎。

关键设计：
- **「数据依据」块在首个 token 之前先给出**（来自本地检索、不依赖网络，总是可用）。
- 检索路径的 `[n]` 编号与记录一一对应，模型被要求在数值后内联标注。
- **Agent 路径的最终回答整段提交而非逐字上屏**（只有轮次结束才知道它是否为最终回答）。
- **最后一轮撤掉工具声明**，让「轮数用尽」与「正常收尾」走同一条路径，不会出现「没有回答」的空档。
- **失败不丢弃已生成内容**：流式中途失败 / 截断都保留已上屏部分并追加显式说明，不静默重来。

### 6.3 异常检测（三条规则）

`DetectAnomaliesUseCase`，对每个成员、每个指标执行：

1. **越界**——与参考范围比较（参考范围按性别取值）；区间型结果（`<0.1` / `>100`）**保守判断**：只有边界值本身已越界才下结论，否则不把「不确定是否越界」误报成确定结论。
2. **趋势**——最近 3 次同向且累计变化超阈值，且三次读数须落在 **180 天时间窗**内（跨两年的三次读数不构成「趋势」）。
3. **个体基线**——当前值对比该成员**自身历史中位数**（≥5 个样本）。群体参考范围回答不了「对你来说是否异常」。

**去重策略 = 7 天窗口 + 严重度穿透**：窗口内同键不重复，但严重度升级必须放行（症状复发能再次报警，病情恶化能升级报警）。

**单位闸门**：记录归一化单位 ≠ 字典标准单位时直接跳过，避免跨单位误报。

**结构化告警**：告警以**结构化事实**落库（指标 / 方向 / 数值 / 参考范围），展示时按当前语言现场渲染——切英文后所有告警（含历史告警）都显示英文。

### 6.4 用药提醒

- 现在是**真正按时刻触发**：`MedicationAlarmScheduler` 用 `AlarmManager.setExactAndAllowWhileIdle`（无精确闹钟权限时降级为近似），每个 (提醒, 时刻) 一个闹钟。
- `MedicationAlarmReceiver` 在触发时以及**开机 / 时区变更 / 改时间 / 应用更新**时重新排期。
- 日历导出写入每日事件 + 提前 5 分钟提醒，用稳定的 `[homehealth:med:<id>]` 标记保证清理幂等；编辑 / 启停 / 删除都会同步日历事件，且带孤儿保护。

## 七、LLM 集成层

- **双协议**：OpenAI 兼容 `chat/completions` 与原生 **Anthropic Messages API**（system 独立传参、base64 图片 `source` 格式、`anthropic-version` 头、扩展思考的 temperature=1 降级重发）。
- **非对称流式**（刻意的选型）：问答走 **SSE 流式**（首字延迟从「整段生成完」降到「首个 token」）；报告解析保持**非流式单次请求-响应**（要的是完整 JSON，半截对象没有意义）。
- **重试策略**：指数退避 + 抖动，**仅限 429 / 5xx / IO**；流式**只在首个增量到达前重试**（已部分上屏时重发会造成重复）。
- **取消**：非流式（`executeCancellable`）与流式都会在协程取消时主动取消在飞的 OkHttp `Call`（阻塞读不会因协程取消而返回，否则连接会挂到 120s readTimeout 才释放）。
- **视觉/文本严格分离**：带图提问会解析视觉路由（问答供应商 → 解析服务兜底），并在回答来源里如实标注——用户配了 A 家却在回答里看到 B 家，不说清会被当成 bug。
- **可观测性**：每次调用把供应商 / 模型 / 场景 / 耗时 / 提示与补全字符数 / 重试次数 / 失败类型写入 `llm_call_logs`——**绝不记录提示词与回复内容**（那里面是用户的健康数据）。设置页按供应商聚合近 30 天统计。
- **Agent 网关**：`ReActAgent` 用文本模型；图片只经 `read_report_image` 工具送往视觉模型（User 条目不带内联图片）。

## 八、ReAct Agent 子系统

手写的 `Thought → Action → Observation` 循环，**不引 LangGraph / AutoGen**（单进程单循环，框架的编排抽象换不来任何东西，却会把「何时该停、失败怎么办」的判断藏进框架内部）。

刻意的设计：
- **最后一轮不提供工具**：与其在轮数用尽后拿着一堆没回填的工具调用收场，不如提前去掉工具声明，逼模型用已有证据作答。
- **工具连续失败会被禁用**（`MAX_TOOL_CONSECUTIVE_FAILURES = 2`）：模型很容易对着同一个错参数反复重试，必须由代码刹车。
- **失败即交给上层降级**：本类不自己编答案，没有证据就回退本地规则引擎。
- **observation 截断**（`OBSERVATION_CHAR_BUDGET = 1500`）：截断时明确标注省略了多少，而不是静默砍掉；**evidence 与模型所见用同一条截断逻辑**，保证用户拿依据核对答案时对得上。

**护栏参数**（`AgentConfig`，集中一处）：最多 5 轮、工具调用上限 8 次、单条观测截断 1500 字符、本地工具超时 10s / 视觉工具 60s。

**工具只读**：异常工具读**已判定**的告警，不重跑检测——`DetectAnomaliesUseCase` 会写库并可能触发通知，直接包成工具等于「问一句话就凭空多出告警」。

## 九、检索层（BM25）

`QaRetriever`：把成员健康记录文本化建索引，按问题做 BM25 Top-K 召回，给出可解释的引用编号。

设计取舍：
- **BM25 而非向量检索**：个人健康记录量级在千条以内，中文体检指标是强关键词场景（问「血糖」就该召回血糖记录）；BM25 无模型依赖、零上传、可解释。云端 Embedding API 会破坏「数据不上传」的承诺。
- **内存索引而非 SQLite FTS**：语料每次提问由单条 `memberId` 索引查询载入，千条量级建索引毫秒级；FTS 表要动 schema。
- **中文切分用「单字 + 相邻双字组合」**：双字粒度保精度（指标名以双字词为主），单字粒度保召回（别名里有单字词：钾 / 钠 / 钙）。
- **文档文本附带指标别名**（复用 `SchemaNormalizer.typeAliases`，不建第二份副本）。
- **强指标词闸门**：泛化总结类问题（「整体健康状况怎么样」）没有可靠指标词，回退全量摘要，而不是放行检索——否则「身体」的单字「体」撞上体重记录，会把上下文窄化成一两个指标。

## 十、归一化层（Schema Normalization）

`SchemaNormalizer`，入库前强制归一化：

1. **指标别名 → 标准类型**：106 条别名映射（中文名 / 英文缩写 / 变体拼写）。
2. **单位写法归一化**：24 种单位拼写统一（`mmol/l → mmol/L`、`umol/L → μmol/L`…）。
3. **跨单位换算**：24 类医学上可靠的换算系数（如维生素 D `nmol/L → ng/mL`）；**没有系数的单位绝不猜测**，保留原值与单位并明确标注。
4. **区间型结果**：`<0.1` / `>100` 连同比较符一起入库（LT/GT），不再因 numericValue 为空被趋势与预警整体跳过。

归一化在解析结果展示前执行，用户核对的是标准化后的数值，入库记录与标准字典单位一致——所以趋势与告警永远建立在同一套测量体系上。

## 十一、隐私与安全

- **`android:allowBackup="false"`**：关闭 `adb backup` / 云备份导出通道。
- **API Key 经 Android Keystore AES-256-GCM 加密**（每次随机 IV，密钥材料不出 TEE，不要求用户认证以免可用性事故）；历史明文 Key 就地平滑迁移；解不开的 Key 被标记为独立状态（`keyUnreadable`），而不是显示「未填写」。
- **两层互不替代的隐私防线**：`allowBackup=false` 挡住备份导出通道，Keystore 加密挡住 root 设备上直接读文件——不同威胁面。
- **版本化首启同意**（`ConsentScreen`）：在能录入任何一条记录之前取得同意，覆盖「数据存哪 / 何时离开设备 / 卸载会发生什么 / 医疗免责声明」四件事；文案有实质变更就递增版本，老用户重新看到。
- FileProvider 未导出；图片写入做路径校验；ProGuard/R8 keep 规则覆盖 Gson DTO、Room 实体、Hilt、WorkManager。

## 十三、工程亮点

1. **连贯、成熟的架构**——清晰三层分层、Hilt、迁移 SQL 单一事实来源、刻意不做破坏性迁移。

## 十四、风险与缺口（按优先级）

### P1 —— 建议尽快处理

1. **测试覆盖只到纯逻辑层**：`LlmClient` 流式 / 重试、仓库行为、ViewModel、Compose UI 均无测试。最高价值的新增是 `LlmClient` 流式与重试测试、少量 ViewModel 测试。
2. **工作区存在大量未提交改动**（见 §15）：含已完成的修复与新组件，建议尽快提交，避免丢失或与历史分析混淆。

### P2 —— 打磨项

3. **参考范围缺权威出处与分层**：`HealthTypes` 内已注明——通用成人参考值、仅性别分层（无年龄 / 孕期），未逐项标注指南出处与版本。儿童 / 老年人 / 孕妇区间与成人不同。
4. **`HealthTypes.labelRes` 对未知类型返回 `0`**：当前所有调用点都经由安全的 `metricLabel()` 兜底，但裸函数对新调用点仍是潜在崩溃点（已有回归测试守住契约）。
5. **每日任务漂移**：24h `PeriodicWorkRequest` 在 DST / 时区变更后可能整体漂移（已加 `DailyCheckScheduler` 统一排期与时间广播重排，可继续观察）。

### 路线图（项目自认）

6. **尚无向量 / 混合检索**（仅 BM25）——最大的 RAG 缺口。
7. 无对外暴露健康工具的 **MCP Server**；无**端侧 LLM**；无 **Health Connect** 可穿戴数据集成。
8. 观感项：`applicationId`（`com.adajunk.homehealth`）≠ `namespace`（`com.example.homehealth`），后者是占位风格命名。

## 十六、总体评价

HomeHealth 是一款**架构良好、文档异常扎实的 Android 应用**，工程质量明显高于一般的个人 / 副业项目。它的差异化是**真实落地**的，而非宣传口号：本地优先隐私的两层独立防线、能避免跨单位误报的归一化层、保守的三规则异常引擎、刻意保留快路径而非「万事皆 Agent」的双路径问答设计，以及不复制敏感数据的 LLM 可观测性。

剩余工作主要属于**维护与深化**，而非正确性：把测试覆盖扩展到纯逻辑之外、提交工作区改动、按项目自身路线图补上向量 / 混合检索以完成 RAG 叙事的最后一块。
