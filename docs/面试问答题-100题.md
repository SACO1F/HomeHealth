## 一、项目深挖 · HomeHealth（Q1-Q30）

### 架构与总览

**Q1.★ 用 30 秒介绍这个项目：它是什么，LLM 在哪里？**
- 本地优先的 Android 家庭健康管家：拍照上传体检报告 → Vision 模型 JSON 模式抽 49 类指标 → Schema 归一化（106 条别名映射、24 类医学换算、无可靠系数绝不猜测）→ 人工确认入库。
- 问答双路径：指向具体指标的问题走 BM25 检索 + 引用溯源；泛化问题交手写 ReAct Agent（4 个只读工具、最多 5 轮、完整护栏）。
- SSE 流式输出，每个数字可溯源；接 7 家供应商、双协议；每次调用有本地可观测日志；首启版本化同意、正式签名分发、发布包 13 类凭据审计零命中。

**Q2.★ 问答为什么是双路径？为什么不全部走 Agent？**
- 快路径：强指标词命中（strongTerms）→ BM25 → 1 次 LLM 请求 → 逐字上屏；Agent 路径：未命中 → ReAct ≤5 轮。
- 实测推演：指向性问题用 Agent 是**负优化**——延迟翻倍（2 次请求 vs 1 次）而质量不变。所以做路由，不是替换。
- 挂靠：路由条件复用当初修「弱字窄化」bug 引入的 strongTerms 闸门——旧机制赋予新职责，不加新层。

**Q3.★ 一次提问从进入到回答的完整链路？**
- 输入（可带图 → 视觉模型三档路由）→ strongTerms 抽取 → 命中：BM25 Top-12 → 四层预算压缩 → 单次生成（temperature 0.3）→ SSE 逐字上屏。
- 未命中：ReAct 循环（工具 → 观测 → 再决策 ≤5 轮）→ 最终答案（非逐字）。
- 收尾：问答历史落库（含引用与附图路径）；llm_call_logs 每次调用埋点（10 维度）。

**Q4.★ 为什么「本地优先」？数据边界划在哪？**
- 健康数据敏感；全部数据只存本机 Room，卸载即删。
- 唯一外发：推理必需的 LLM 请求，直连**用户自己配 Key 的**供应商——不经过任何开发者服务器、无统计上报。
- 加分点：README 曾写「不上传任何服务器」，后订正为「不经过开发者服务器、直连用户自配厂商」——措辞精确性本身就是可讲的素材。

**Q5.★ 面试官质疑：LLM 应用都是 Python 生态，你为什么用 Kotlin？**
- 岗位核心是协议理解、检索与 Agent 设计、工程质量——语言是载体。我用 Kotlin 独立实现了 Python 生态的等价物：手写 ReAct、双协议流式 Function Calling、SSE——证明理解在架构层而不在框架层。
- 手撕题我会用 Python 写（已在练）。
- 若岗位偏端侧/移动端，这反而是优势。

### ReAct 循环与护栏

**Q6.★ 你的 ReAct 循环怎么保证会停？**
- 三重护栏：MAX_TURNS=5 硬上限；**最后一轮不提供工具声明**，模型只能作答；工具调用总数上限 8（防单轮并行 × 多轮叠加）。
- 轮数用尽不报错——用已有证据收尾，与正常结束走同一条代码路径，不会出现「没有回答」的空档。

**Q7.★ 最后一轮为什么撤掉工具声明？**
- 不撤的后果：轮数用尽时模型可能还在发工具调用，而没机会回填 → 收场是「一堆未执行的工具调用 + 没有答案」。
- 撤掉后模型被迫基于已有观测作答 → 「轮数用尽」与「正常收尾」合流。

**Q8.★ 工具轮的正文为什么不能进最终答案？**
- 中间轮的"正文"是思考碎片，若先流到答案区、发现是工具轮再撤回，用户看到明显抖动。
- 实现：工具轮正文并入思考轨迹，只有最终轮（无工具调用）才进 Answer 区。牺牲 Agent 的逐字流式换正确性，快路径仍逐字。

**Q9.★ 模型传错工具参数怎么办？**
- ToolArgs 容错解析：缺字段/类型不符返回 null 而不是抛异常。
- 参数错误作为**失败观测**回填给模型让它自我修正；同一工具连续失败 2 次即禁用（防止反复撞同一面墙）。

**Q10.★ 工具返回为什么要截断？怎么标注？**
- 一次 search_records 多项 × 多条就能撑爆上下文 → 单个 observation 上限 1500 字符。
- 截断时明确标注省略了多少——模型需要知道「还有更多」，否则它以为世界就这么多数据。

**Q11.★ Agent 的最终回答为什么不做逐字上屏？**
- 只有一轮结束后才知道它是不是最终回答；中间轮推理先上屏再撤回 = 抖动。
- 分层体验：快路径逐字（结构确定），Agent 不逐字（结构不定）。这是明确取舍，不是没做。

**Q12.★ Agent 和快路径怎么选？路由条件是什么？**
- QaRetriever.strongTermsOf 抽不到强指标词 → 泛化/多步问题 → Agent。
- 反面论证要备好：为什么不全局上 Agent（Q2 的负优化实测）。

**Q13.★ AgentConfig 里 5 个数字各防哪种失控？**
- 轮数 5：成本随轮数超线性；工具调用 8：防并行×多轮叠加；observation 1500 字符：防一次查询撑爆上下文；连续失败 2 次禁用：模型会对着同一错参数反复重试；超时 10s/60s：本地工具 vs 网络请求。
- 这题的加分点：每个数字都对应一个**具体失控方式**，不是拍脑袋的默认值。

**Q14.★ 怎么测试一个 Agent 循环？**
- 把 LLM 决策抽成 AgentLlmGateway 接口 → 假网关按脚本返回事件序列 → 循环本体可断言。
- 7 条循环级策略测试：两轮收敛、末轮不含工具、工具轮正文不进答案、工具异常转观测继续、连续失败禁用、无证据抛出、observation 超预算截断。
- 价值：Agent 的难点全在「什么时候停、失败了怎么办」，这些分支靠真机凑场景贵且不可复现。

**Q15.★ 多轮 Agent 的成本和可靠性怎么算？降级矩阵有哪些分支？**
- 成本超线性：每轮重发工具 schema + 全部历史 observation。可靠性叠加：4 轮 × 99% ≈ 96%。
- 降级矩阵：工具失败 → 失败观测回填继续；轮数用尽 → 末轮撤工具强制作答；证据为空 → 明说「数据不足」而非编造；供应商失败 → 重试/切换。

**Q16.★ 为什么工具必须只读？**
- DetectAnomaliesUseCase 会写库：createAlert + 7 天去重 + 严重度穿透 + 可能触发系统通知。若按直觉包成工具：用户问一句「有什么异常」→ 凭空生成一批告警 = 用查询姿势触发写操作。
- 所以工具是 get_alerts（读已判定结果），检测交给每日后台与录入流程。**医疗场景：确定性系统做确定性判断。**
- 这是最值钱的一条——只有真读过代码才发现的问题。

**Q17.★ 读报告图片为什么做成工具，而不是内联 base64？**
- 单轮场景内联更省（1 次请求）；但 ReAct 多轮下 base64 会随每轮重发。
- 工具形式把图片一次转成文本，后续轮次保持纯文本。结论：判断随场景变，不背标准答案。

### 检索、上下文与数据

**Q18.★ 你的 Naive RAG 长什么样？**
- BM25（k1=1.5, b=0.75）+ 中文分词 + 强指标词闸门（strongTerms，防泛化词稀释）+ 引用溯源（每个数字回链具体记录）。
- 语料是结构化健康记录，查询多为指标词——这正是 BM25 的主场。

**Q19.★ 为什么不用向量检索？什么条件会切换？**
- 四点反向论证：语料千条内（暴力余弦都 <1ms）；查询是强关键词场景（BM25 更准）；云端 Embedding 破坏「数据不上传」承诺；避免多一次 DB 迁移。
- 切换条件：C1（rawText 落库）完成后叙述文本检索需求实证出现；语料上量；同义改写型查询占比升高。
- 若追问方案：端侧 bge-small-zh-v1.5（512 维 / 24M / INT8≈23MB）+ RRF 与 BM25 融合。

**Q20.★ 上下文预算分几层？**
- 四层：检索 Top-K=12 → 每指标 Top-10 → 摘要 6000 字符 → 单 observation 1500 字符。
- 每层对应一种膨胀源：召回过多、单项过多、历史过长、单条工具结果过大。

**Q21.★ 上下文污染怎么防？**
- 单位不一致（mg/dL vs mmol/L）时**跳过**「偏高/偏低」标注——宁可少说不错说。
- observation 预算防单次膨胀；工具轮正文不进答案区（Q8）。

**Q22.★ 「一份检索代码两种用法」指什么？**
- 同一 BM25 检索层：快路径直接用它；Agent 把它包成 search_records 工具。
- 设计含义：检索与编排解耦，新增用法零重复代码。

**Q23.★ 数据库为什么升到 v8？迁移纪律是什么？**
- 8 个版本 = 需求演进（指标/告警/问答历史/附图路径…）。
- 纪律：每次迁移导出 schema 快照 + JVM 结构级测试 + androidTest 真机校验 + 刻意不用破坏性迁移兜底。
- 已知坑：升版后首次构建可能漏 schema asset（mergeAssets 不依赖 ksp 生成任务）→ 构建两次。

**Q24.★ ParseResult.rawText 不落库是怎么回事？怎么讲这个已知缺陷？**
- 事实：模型转录的完整报告文本（结论/印象/建议）只过了确认页，confirmRecords 只写 extractedJson → 影像/病理「读一次丢一次」，检索层拿不到。
- 话术：审计时自己发现的 → 已立项 C1（Room v9 加列）并排在向量实验之前 → 教训：结构化抽取时顺手保留原文，成本几乎为零。
- 关键：把缺陷讲成「我发现、我排期」，不是被问出来才承认。

**Q25.★ 7 家供应商、双协议怎么抽象？**
- LlmClient 统一出口 + AgentRequestBody 做双协议翻译（声明/调用/回填/system 四条差异各收在一处）+ LlmStreamParser 按协议分派 + ToolCallAssembler 做协议无关的分片累积。
- 新增供应商 = 加一个翻译器 + parser 分支；协议差异被压进两个文件，不扩散。

### 视觉路由与合规分发（v4 新增）

**Q26.★ 发图提问的模型路由怎么设计？**
- 问答服务配的是文本模型，图片必须走视觉模型。三档：① 问答模型本身支持 vision → 直接用；② 回退报告解析服务 + **来源如实标注**；③ 都没有 → 明确文案引导。
- 铁律：绝不静默丢图——让用户以为模型看过图，在健康场景代价很高。

**Q27.★ 首启同意为什么做版本化？机制是什么？**
- CONSENT_VERSION_CURRENT 常量 vs 本地已同意版本号比较；文案有实质变更 → 递增版本号 → 老用户重看。
- 内容四段：数据只存本机 / 何时联网 / 卸载即删 / 非医疗建议。合规不是一次性弹窗。

**Q28.★ 权限为什么在同意之后才申请？**
- 同意前置 = 有意义的同意；未同意时 MainActivity 不渲染 RootApp、也不申请通知权限。
- 追问「同意前用户什么也用不了怎么办」：退出按钮 + 说明文案，健康场景宁严勿松。

**Q29.★ 发布包怎么证明没有泄漏凭据？**
- 自写审计脚本扫 APK：13 类模式（sk-/AIza/ghp_/AKIA/xox/BEGIN PRIVATE KEY/Bearer/password 字面量/构建者路径/appsecret 等）→ 实测零命中。
- sha256 校验链 + 签名指纹公开可核。防的是「打包时把测试密钥带进去」。

**Q30.★ keystore.properties 缺失时构建会怎样？R8 开启后最大的回归风险？**
- properties 缺失 → hasReleaseSigning=false → release 不挂签名配置 → 公开仓库贡献者仍能构建（未签名包）。这是有意的降级设计。
- R8 风险：Gson 反序列化按字段名映射，混淆后字段名变了 → 得到 null/默认值 → keep 规则 + 真机回归第一项。

## 二、阶段 1 · LLM 基础 + Agent 入门（Q31-Q50）｜对应 mianshi.md 第 1 周，hello-agents ch1-3

**Q31. 写出 Self-Attention 公式；为什么要除以 √d_k？**
- Attention(Q,K,V) = softmax(QK^T/√d_k)V。
- 点积方差随维度增大 → 除以 √d_k 使方差回到 O(1)，防止 softmax 进入饱和区、梯度消失。

**Q32. Multi-Head Attention 好在哪？**
- 多个子空间并行建模不同关系（句法/指代/位置等）；每头维度 = d_model/h，总计算量近似不变；头间独立 → 并行友好。

**Q33. 三种架构；LLM 为什么主流是 Decoder-only？**
- Encoder-only（BERT，理解）/ Decoder-only（GPT，生成）/ Encoder-Decoder（T5，转换）。
- Decoder-only 主流：训练目标统一（next-token）数据效率高；因果掩码下 KV Cache 推理友好；架构简单易堆叠、scaling 表现好。

**Q34. 位置编码的演进？长上下文怎么外推？**
- 正弦绝对编码 → 可学习 → RoPE（旋转编码，内积只依赖相对位置）→ ALiBi（线性偏置）。
- 长上下文：RoPE + 位置插值（PI）/ YaRN 缩放频率；配合 Sliding Window 省显存。

**Q35. Pre-LN vs Post-LN？RMSNorm 改了什么？**
- Post-LN 深层训练不稳，Pre-LN 梯度更稳成为主流。
- RMSNorm 去掉均值中心化只做方差缩放 → 计算更省，效果持平（LLaMA 系采用）。

**Q36. 注意力 O(n²) 有哪些优化？**
- FlashAttention：IO 感知分块 + online softmax，精确非近似，大幅省 HBM 读写与激活显存。
- MQA/GQA：KV 头共享，KV Cache 按 kv_heads 等比缩小；Sliding Window：局部注意力。

**Q37. BPE 的原理？为什么中文 token 成本高？**
- 从字符/字节初始词表，迭代合并语料中最高频相邻对，直到目标词表大小。
- 中文在英文主导词表里常退化为 byte 级多 token → 费用高、窗口消耗快；解法：中文扩词表（Qwen 等）。

**Q38. LLM 训练三阶段各优化什么？**
- 预训练：next-token，学语言与世界知识；SFT：指令对齐，学会「听人话办事」；RLHF/DPO：偏好对齐，学人类偏好与安全边界。
- DPO：用偏好对直接优化策略，省掉 reward model 与 RL 循环。

**Q39. top-k / top-p / temperature 怎么选？**
- temperature 缩放 logits 分布；top-k 保留固定数量；top-p（nucleus）保留累积概率 ≥ p 的最小集合，动态截断更稳。
- 经验：结构化抽取/工具调用低温度（0-0.3）；创意生成 0.7+。挂靠：解析 0.1 / 问答 0.3。

**Q40. temperature=0 时输出为什么仍可能不确定？**
- 浮点加法非结合，batch/reduce 顺序影响结果；不同 batch shape 走不同 kernel（continuous batching 会改变 batch 组成）；MoE 路由与并行非确定。
- 结论：temperature=0 是贪心采样，不是 bit 级确定。

**Q41. KV Cache 的原理与显存估算？**
- 自回归生成缓存历史 K/V，避免每步重算全序列 → 代价是显存随上下文线性增长。
- 显存 = 2（K和V） × layers × kv_heads × head_dim × seq_len × batch × 每元素字节数；算例见 Q87。

**Q42. 幻觉的成因与缓解？**
- 成因：似然目标 ≠ 事实性、知识截止/长尾、采样随机、指令诱导。
- 缓解：RAG + 引用溯源、结构化/约束输出、低温度、自检与自我一致性、明确拒答规则。挂靠：「无可靠系数绝不猜测」「观测全空不许下结论」。

**Q43. lost in the middle 是什么？对策？**
- 多文档上下文中部信息利用率呈 U 型低谷。
- 对策：关键内容放首尾、控制 top-k、rerank 精排减少噪声、分层摘要。

**Q44.★ max_tokens 截断在工程上怎么处理？**
- 识别 finish_reason=="length" / Anthropic stop_reason=="max_tokens" → 这是截断不是完整答案。
- 处理：软告警 + 降级策略（提示用户/重试更长预算），绝不当完整结果用。挂靠：项目的截断检测与降级。

**Q45. Agent 的定义与核心组件？**
- 以 LLM 为决策核心的感知-规划-行动闭环。四组件：规划（分解/反思）、记忆（短期=上下文窗口、长期=外部存储）、工具使用、行动执行。

**Q46. LLM Agent 发展史的关键节点？**
- 2017 Transformer → 2022 ReAct/Toolformer/ChatGPT → 2023 AutoGPT/BabyAGI 自主浪潮、AutoGen/MetaGPT 多智能体框架 → 2024 MCP 发布、o1 慢思考、Computer Use → 2025 MCP 生态化、A2A、Claude Skills。

**Q47.★ Agent、Workflow、聊天机器人的边界？**
- 聊天机器人：无工具单轮对话；Workflow：固定控制流编排（LLM 是节点）；Agent：LLM 自主决定下一步（循环+工具+终止条件）。
- 挂靠：能正面回答「我的项目哪里是 Agent」——路由后的 ReAct 循环就是；也保留「它不是 Multi-Agent，也没必要是」的判断。

**Q48. CoT / ToT / ReAct 是什么关系？**
- CoT：示例引导的推理链（一次性生成）；ToT：树状探索+回溯；ReAct：思考-行动-观察交错并**与环境交互**——CoT 只想，ReAct 想完还能动手验证。

**Q49. Multi-Agent 什么时候值得用？代价？**
- 值得：任务可并行（map-reduce 研究）、需要对抗/审校角色（generator-critic）、上下文超单窗口需隔离。
- 代价：通信 token 爆炸、误差级联、调试难、延迟叠加。默认先做单 agent + 好工具。

**Q50. 六篇经典论文各贡献了什么？**
- CoT（Wei'22）：推理链示范；ReAct（Yao'22）：推理+行动交错；Toolformer（Schick'23）：自监督学会插 API 调用；Reflexion（Shinn'23）：语言反馈存记忆、无梯度自我改进；Voyager（Wang'23）：技能库+自动课程的终身学习；Generative Agents（Park'23）：记忆流+反思+规划（斯坦福小镇）。

## 三、阶段 2 · 范式手撕 + RAG 进阶（Q51-Q72）｜对应第 2 周，ch4/8/9

**Q51. 现场手写一个 ReAct 循环（伪代码）。**
- 骨架：`for step in 1..MAX_TURNS: out = llm(msgs, tools = step<MAX ? tools : None)`；有 tool_calls → 执行（try/except 把异常转观测）→ 截断回填；无 tool_calls → 返回正文；循环走完 → 用已有证据降级作答。
- 面试必说四个细节：末轮撤工具、异常转观测、observation 截断、降级出口。

**Q52. ReAct 的典型失败模式与对策？**
- 死循环/重复调用 → 连续失败禁用 + 总调用上限；格式漂移 → 容错解析；错误传播（一步错步步错）→ 失败观测回填修正；上下文爆炸 → observation 预算。
- 挂靠：五个数字护栏 + 7 条策略测试就是这些对策的落地。

**Q53. Plan-and-Solve 的原理？什么任务适合？**
- 先让 LLM 生成完整计划，再按步执行（可逐步修订）；适合目标明确、步骤可预规划的任务（数学、行程）。
- 与 ReAct 本质差异：先全局计划 vs 边看数据边决定。

**Q54.★ 你的项目为什么不需要 Plan-and-Solve？**
- 问题形态是「先看数据再决定下一步」：查什么工具取决于上一轮观测，计划写死反而失去对数据的适应力。
- 承认边界：若做「一周健康报告生成」这类多步产出任务，PaS 值得引入。

**Q55. 完整版 Reflection 怎么设计？**
- 三段：draft 生成 → critique（对照证据清单自查：引用够不够、数字对不对）→ revise；停止条件 = 通过检查或轮数上限。
- 成本：一次额外 LLM 请求；收益：降低无证据作答率。

**Q56.★ 你只做了轻量 Reflection，怎么为这个取舍辩护？**
- 已做：observations 全空时禁止下结论（防无数据编建议）——这是最高频的失败模式，先用零成本手段堵住。
- 完整版要一次额外请求，在 5 轮预算内会挤掉工具调用轮 → 承认这是取舍不是遗漏，并说清什么条件值得加（错误率实测高了就加）。

**Q57. Reflexion 和 Reflection 的区别？**
- Reflection：单次任务内的自省修订；Reflexion：跨 trial 的语言化反馈存入情景记忆，无梯度地改进下一次尝试（agent 级自我改进）。

**Q58. 三种范式的同构性？你会怎么抽公共基类？**
- 三者都是 generate → （parse action / critique）→ observe → loop 的变体，差异只在「决策依据」和「停止条件」。
- 抽法：BaseAgent（循环、护栏、观测预算、降级出口）+ 各范式一个 decide() 策略，各 ~50 行。挂靠：你的手写循环已具备这个骨架的雏形。

**Q59. 现场手撕 Naive RAG（三步）与每步的坑。**
- ① 切块入库：split → embed → 存索引。坑：切断表格/语义 → 递归分隔 + overlap。
- ② 检索：query embed → 相似度 top-k。坑：同义改写召不中 → multi-query/混合检索。
- ③ 生成：拼上下文 + 问题。坑：超窗（预算压缩）、无引用（要求带来源）。

**Q60. Naive RAG 失败点如何映射到 Advanced RAG 对策？**
- 检索前：query 改写/HyDE/路由（解决 query 与文档词汇错配）；检索中：hybrid + rerank（解决召回与排序）；检索后：压缩/去重/引用（解决上下文质量）。
- 挂靠：项目已有 Pre-Retrieval 路由（强词闸门=意图路由）与两级路由，缺 Hybrid/Rerank——如实说，别背成全做过。

**Q61. Chunking 策略怎么选？**
- 谱系：固定长度+overlap / 递归字符（段落→句子）/ 语义切分 / 父子块（小块检索、大块回填）/ 结构感知（标题/表格/代码）。
- 权衡：太小语义碎、太大噪声稀释+超窗；典型 256-512 token、overlap 10-20%。结构化数据先考虑不切块（按记录检索）。

**Q62. Embedding 模型怎么选型？**
- 维度（存储/速度 vs 精度）、语言（中文看 C-MTEB）、榜单只作初筛（自有数据评测为准）、部署形态（API vs 本地 vs 端侧——数据合规）、最大输入长度。
- 挂靠：项目结论——云端 embedding 破坏数据边界；端侧候选 bge-small-zh-v1.5（24M/512 维/INT8≈23MB）。

**Q63. Hybrid 检索怎么做？RRF 是什么？**
- BM25 抓强关键词/术语，向量抓同义改写，两路召回。
- RRF：score(d) = Σ 1/(k + rank_i(d))，k≈60——只用排名不用分数，免归一化、鲁棒。

**Q64. Rerank 为什么有效？cross-encoder 和 bi-encoder 差别？**
- bi-encoder 各自独立编码 → 可离线建索引、快，但交互浅；cross-encoder 拼接后交叉注意力 → 准但必须在线逐对。
- 两段式：召回 100 → 精排 top-10。什么条件加：语料上量或精度要求提高时（bge-reranker 类）。

**Q65. Query 侧优化有哪些？**
- 改写（口语→检索友好）、multi-query 扩展（并集召回）、HyDE（先生成假想答案再检索，解决问答复配错位）、路由（意图分类到不同检索器）、multi-hop 分解（子问题链迭代检索）。
- 代价：每步都是额外 LLM 调用 → 延迟/成本，按需启用。

**Q66. 向量库选型的决策维度与主流对比？**
- 维度：规模、标量过滤、持久化与运维、混合检索、生态。
- 对比：FAISS=库非服务（单机内存、原型）；Milvus=分布式（亿级+过滤）；pgvector=复用 PG（过滤强、中等规模）；Chroma=轻量原型；ES=已有全文栈加混合。
- 面试官真正想听的是「你的项目为什么选 X」——见 Q72。

**Q67. HNSW 和 IVF 的原理一句话版？**
- IVF：先聚类成 nlist 个簇，查询只扫 nprobe 个最近的簇 → 快但可能漏。
- HNSW：分层跳表式近邻图，查询沿高层到低层贪心下行 → O(logN) 近似查询，ef/M 调召回-速度-内存。

**Q68. RAG 的评估指标（RAGAS 口径）？**
- 检索侧：context precision（相关块是否排前）、context recall（该检回的是否检回，需标注答案）。
- 生成侧：faithfulness（答案是否被上下文支撑，反幻觉）、answer relevancy（答的是不是所问）。

**Q69.★ 没有标注数据怎么评检索质量？**
- 项目的现实做法：引用溯源天然可校验——答案里的数字必须能在被引用记录中找到（可脚本化校验数字匹配率）；人工抽检 30-50 条真实问题。
- 这是「用领域约束替代标注」的思路，比背 RAGAS 加分。

**Q70. GraphRAG 和 Agentic RAG 是什么？**
- GraphRAG：抽实体关系建图+社区摘要，答全局性/多跳问题（微软 2024）；代价：构建维护成本高，小语料不值。
- Agentic RAG：检索作为 agent 工具，自主决定检索什么、几轮、够不够（Self-RAG/CRAG 思路）；挂靠：你的 Agent 路径本质就是 Agentic 检索。

**Q71. RAG、微调、长上下文怎么决策？**
- 知识私有/常变/需溯源 → RAG；行为风格/输出格式/领域术语稳定且数据多 → 微调；文档少且一次性、塞得进窗口 → 长上下文直接给。
- 常见组合：RAG（知识）+ 轻量微调（工具调用可靠性/格式）。挂靠：项目选 RAG——数据本机、免训练设施、需逐数字溯源。

**Q72.★ 「千级语料不需要向量数据库」的完整论证。**
- 算账：1000 × 512 × 4B ≈ 2MB 内存索引；暴力余弦 <1ms——数据库要解决的问题（规模/并发/持久化）一个都不存在。
- 论证链：先算规模 → 再看查询形态（强关键词）→ 再看约束（数据边界）→ 最后给切换条件（Q19）。这题展示的是「用数字做决策」，比选型表值钱。

## 四、阶段 3 · 工具协议 + 框架（Q73-Q84）｜对应第 3 周，ch6/10 + Extra05/08

**Q73. Function Calling 的完整流程？模型真的「执行」了工具吗？**
- 流程：请求带工具 schema → 模型输出结构化调用（name + JSON 参数）→ **客户端**执行 → 结果回填 → 模型继续生成。
- 强调：模型只输出调用意图，执行永远在你的代码里——安全边界（挂靠 Q16 工具只读）。

**Q74.★ OpenAI 与 Anthropic 工具调用的四条差异？**
- 声明：`tools[].function.parameters` vs `input_schema`；流式分片：`delta.tool_calls[]` 按 index 拼 arguments vs `input_json_delta.partial_json`；回填：`role:"tool"`+tool_call_id vs user 消息里的 `tool_result` 块；system：独立消息 vs 首条 user 内的 system 块。
- 挂靠：AgentRequestBody 把四条差异各收在一处。

**Q75.★ 流式 function calling 为什么不累积必错？**
- 参数 JSON 是**分片**返回的：OpenAI 的 arguments 按 index 逐片拼接，Anthropic 是 input_json_delta 逐段——看到一段就 parse 必然失败。
- ToolCallAssembler 累积到流结束才产出完整调用，并为此写了单测。这是流式 FC 最容易写错的地方。

**Q76. MCP 是什么？解决什么问题？架构角色？**
- Model Context Protocol，Anthropic 2024-11 开源；把「M 个应用 × N 个工具」的集成爆炸降为 M+N（USB-C 类比）。
- 角色：Host（LLM 应用）内嵌 Client，与 Server（工具提供方）1:1 通信；JSON-RPC 2.0；传输 stdio（本地）/ Streamable HTTP（远程）。

**Q77. MCP 的三种原语？**
- tools（模型控制：可调用的函数）、resources（应用控制：类文件上下文数据）、prompts（用户控制：预置模板）。
- 另有 sampling/roots：server 反向借用 host 的 LLM 与文件系统能力——说得出这个是加分层。

**Q78. A2A 是什么？与 MCP 什么关系？**
- Agent-to-Agent，Google 2025-04 开源：agent 间任务委托协议。Agent Card 自描述能力、Task 生命周期、返回 artifact。
- 互补而非竞争：MCP 连 agent↔工具/数据，A2A 连 agent↔agent；A2A 强调 opaque（不暴露对方内部记忆与工具）。

**Q79. Agent Skill 是什么？与 MCP 怎么辨析？**
- Anthropic 2025-10：一个文件夹（SKILL.md + 脚本/资源），模型按需渐进式加载——本质是给模型注入**程序性知识/最佳实践**。
- 辨析：MCP 给连接（能力从哪来），Skill 给方法（这类事怎么做好）；Skill 可以指导模型更好地使用 MCP 工具。

**Q80. SSE / WebSocket / 长轮询怎么选？**
- LLM 流式输出是单向推送 → SSE 默认选：基于 HTTP、代理穿透好、自动重连（Last-Event-ID）。
- WebSocket：双向场景（语音/协作）才值得协议升级与基建改造；长轮询：兼容性兜底，延迟高。
- 实战坑：Nginx 反代默认缓冲会「攒一波再吐」→ 关缓冲（X-Accel-Buffering: no）；心跳防断连。

**Q81.★ 你的解析路径为什么刻意保持非流式？**
- 解析是一次性结构化任务（等完整 JSON），流式对用户无增益还引入分片复杂性；问答是对话任务，流式增益明显。
- 结论：流式与否跟着**任务形态**走，不跟技术时髦走。

**Q82. LangGraph 的核心抽象？适合什么？**
- StateGraph：节点+边+共享状态，原生循环支持；checkpoint 持久化（可暂停/恢复/时间旅行）；human-in-the-loop 中断审批。
- 适合需要确定性控制流 + 持久化 + 审批的多步流程。

**Q83. AutoGen 的核心抽象？与 LangGraph 怎么选？**
- AutoGen：conversable agent 之间以对话协作，GroupChat 调度，嵌套聊天——适合快速原型多角色对话。
- 选型：要可控、可测、可恢复 → LangGraph；要快速搭多角色对话原型 → AutoGen；AgentScope 走消息传递+显式工作流+分布式。

**Q84.★ 手写循环 vs 用框架的完整答辩话术。**
- 我的场景：单进程单循环、5 个护栏数字、明确终止条件——框架换不来任何东西，反而把「什么时候停、失败了怎么办」藏进框架黑盒。
- 底气：这轮我真的手写了一遍（ReActAgent + 7 条策略测试），并且我能说出框架会替我做什么（Q82/Q83）——所以「不用」是选型，不是不会。
- 若被追问「生产会不会用框架」：多 agent 编排/需要审批中断时 LangGraph 值得引入——给出条件而不是立场。

## 五、阶段 4 · 工程化（Q85-Q96）｜对应第 4 周，ch12（评估）+ 外部 vLLM 资料

**Q85. vLLM 为什么快？**
- 三件套：PagedAttention（KV Cache 分页管理，消灭显存碎片 → 更大 batch）；Continuous Batching（token 级调度，完成的立即退出、新请求随时加入）；prefix caching（共享前缀 KV 复用）。
- 追问往下两层见 Q86/Q87。

**Q86. PagedAttention 的细节？**
- 把 KV Cache 切成固定大小 block（如 16 token/块），逻辑连续、物理不连续，靠 block table 映射——像操作系统虚拟内存分页。
- 收益：内部/外部碎片近乎归零 → 显存利用率高 → 并发大增；支持 copy-on-write 共享前缀（多请求共用 system prompt 的 KV）。

**Q87. 算一遍 KV Cache 显存与并发能力。**
- 公式：2 × layers × kv_heads × head_dim × seq × batch × bytes。
- 例：Llama-2-7B（32 层/32 头/d=128/fp16）= 每 token ≈ 0.5MB/请求；4k 上下文 → ~2.1GB/请求。
- 80GB 卡：权重 14GB → 剩 ~60GB → 理论 ~28 路；换 GQA（8 kv 头）KV 缩 4 倍 → 100+ 路（数量级即可，激活/碎片另算）。这道算术题是「真懂 vLLM」的分水岭。

**Q88. 量化方法谱系怎么选？**
- GPTQ：训练后逐层量化，Hessian 误差补偿，INT4 GPU 推理标配；AWQ：激活感知，保护少数显著通道，INT4 精度稳；SmoothQuant：把激活 outlier 平滑迁移到权重，W8A8 全整数高吞吐；FP8：H100 级原生，训练推理都能用。
- 经验：单卡 7B-70B 服务 → AWQ/GPTQ INT4；追求吞吐 → W8A8/FP8；精度敏感 → INT8/FP8 起步。

**Q89. 投机解码的原理与适用条件？**
- 小 draft 模型连草 k 个 token → 大模型一次并行验证 → 按拒绝采样修正，保证输出分布与目标模型完全一致。
- 适用：显存富余、batch 小、延迟敏感；大 batch 高吞吐场景不划算（验证占算力）。

**Q90. 推理服务核心指标？分别受什么影响？**
- TTFT（首 token 延迟）：prefill 时长 + 排队 → 输入长度、prefix cache、chunked prefill；TPOT/ITL（每 token 间隔）：decode 速度 → batch 大小、显存带宽；吞吐 tokens/s：系统级。
- 优化对应：continuous batching、量化、prefix caching、prefill-decode 分离。

**Q91.★ LLM 应用的可观测性该记什么、不该记什么？**
- 记元数据：供应商/模型/耗时/流式首包/错误分类/token 数/轮次——按调用与按轮聚合，能回答「一次提问 5 轮，哪轮慢、哪轮失败」。
- 不记内容：健康数据隐私边界——日志只记「发生了什么」，不记「说了什么」。
- 挂靠：llm_call_logs 10 维度 + Agent 每轮同口径埋点。

**Q92. RAG 和 Agent 分别怎么评？pass^k 是什么？**
- RAG：检索（context recall/precision）+ 生成（faithfulness、answer relevancy）——Q68。
- Agent：任务成功率、轨迹效率（步数/成本）、护栏通过率、**pass^k = 连续 k 次全过的概率**（可靠性指标，区别 pass@k 的「有机会过」）——对生产化更相关。
- Benchmark 认识几个即可：AgentBench、GAIA、SWE-bench、WebArena、τ-bench。

**Q93. LLM-as-judge 有哪些偏差？怎么缓解？**
- 位置偏差（偏爱某个位置）、长度偏差（偏爱长答案）、自我偏好、知识泄漏。
- 缓解：交换位置双评取平均、成对+绝对打分混合、rubric 细化、多裁判投票。

**Q94. LoRA 的原理？为什么省显存？QLoRA 呢？**
- 冻结原权重 W，训练低秩增量 ΔW=BA（B: d×r，A: r×k，r≪min(d,k)）。
- 省显存：可训练参数骤减 → 梯度与 Adam 优化器状态（2 份动量）同比骤减；r 常取 8-64；可插拔多任务。
- QLoRA：4bit（NF4）冻结底座 + LoRA + 分页优化器 → 单卡微调 65B。

**Q95.★ 给你自己的 Agent 建一个最小评测，你会怎么做？**
- ① 已有的 7 条策略测试作为回归评测（假网关，零成本跑 CI）；② 从 llm_call_logs 抽真实问题人工标 30-50 条「应走快路径/Agent」做路由回归；③ 忠实度脚本化抽检：答案数字必须能在引用记录里找到；④ 上线前全量跑这组。
- 这题是把 ch12「评估」照进项目——有 llm_call_logs 的数据底子，说这话有据。

**Q96. LLM 应用的成本优化组合拳？**
- prompt caching（system/工具 schema 前缀复用）、路由分流（简单问题小模型/快路径——挂靠 strongTerms）、输出长度控制（max_tokens+结构化输出）、离线批处理 API、语义结果缓存。
- 监控先行：token 大头通常在输入（80%+），先看数据再优化。
